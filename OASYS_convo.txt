  app/process/page.tsx:104 — it's a <Link href={returnTo}> instead of
  history.back(). The result screen records its own URL when it saves the stage
  frames, so the arrow goes back to the exact screen you came from, query string
  included — for a report that's ?lat=…&lng=…&address=…, which carries the
  location you pinned. A bare path would have dropped it. It also labels itself
  "Back to the report" or "Back to the result" depending on which screen it
  returns to, since both lead here.

  But the arrow alone wouldn't have worked. Wiring it up exposed that the
  destination was broken: the result screen calls clearPendingScan() after
  analysing, so re-mounting it found nothing and showed "No image found to 
  analyze. Please upload one again." That applied to the browser's back button
  too — it was already broken before this page existed, and I only found it by
  tracing what the link would land on.

  So the finished result is now kept in sessionStorage
  (utils/pendingAnalysis.ts:71), keyed by path so a scan's result can't surface
  on the report screen. Returning restores it instantly with no re-analysis.

  That in turn opened a worse hole: a restored screen would show the Submit
  button again and let the same report be filed twice. The stored result
  therefore carries a submitted flag, and a restored screen that was already
  filed comes back showing the confirmation, not the button.

  I also hardened the stored return URL — only same-site absolute paths are
  accepted, so a tampered or stale value can't turn the arrow into an open
  redirect.

  Verified with 12 tests against the real compiled parseStagePayload (not a
  copy): report URLs with query strings survive intact, https://, //host and
  javascript: are all rejected to /, malformed and empty payloads return null.
  Confirmed in the built chunk that the arrow ships as href:i bound to the
  variable with zero remaining history.back calls.
